# 详细解释一下沙箱的概念

> 详细解释一下沙箱的概念

沙箱（sandbox）是一种“受限制的执行环境”：程序可以运行，但只能在预先允许的范围内访问文件、网络、进程、设备和系统设置。即使程序出错或行为恶意，也尽量把影响限制在沙箱边界内。

可以把它理解成儿童游乐场：

- 程序是游乐场里的活动者；
- 围栏是权限边界；
- 游乐设施是被允许使用的资源；
- 围栏外的道路、建筑和设备默认不能接触。

**沙箱主要解决三个问题：**

1. **限制文件访问**
   程序只能读取或修改指定目录，不能随意访问用户的密码、浏览器数据或其他项目文件。

2. **限制系统操作**
   默认禁止安装系统级软件、修改注册表、创建管理员账户、改变防火墙或关闭安全功能。

3. **限制网络和外部通信**
   可以完全断网，也可以只允许访问特定网站或接口，防止程序上传敏感数据或下载未知内容。

在编程代理环境中，沙箱通常会细分为几类权限：

- **读权限**：可以查看文件，但不能修改。
- **写权限**：可以创建、修改或删除指定目录中的文件。
- **执行权限**：可以运行命令或程序。
- **网络权限**：可以访问互联网或外部服务。
- **管理员权限**：可以修改系统级设置，风险最高。

例如，一个项目沙箱可能允许代理：

```text
读取项目代码
修改项目目录
运行测试
```

但不允许：

```text
读取其他用户目录
访问浏览器密码
修改 Windows 系统设置
直接向互联网发送数据
```

某些操作需要额外确认，是因为它们可能超出普通项目修改范围，例如：

- 删除大量文件；
- 卸载软件；
- 修改系统设置；
- 使用管理员权限；
- 访问外部网络；
- 写入项目目录之外的位置。

沙箱和相关技术经常被混淆：

| 技术     | 主要作用                         | 隔离强度             |
| -------- | -------------------------------- | -------------------- |
| 沙箱     | 限制程序权限和可访问资源         | 取决于实现           |
| 容器     | 隔离进程、文件系统和部分系统资源 | 通常强于普通权限限制 |
| 虚拟机   | 模拟完整独立操作系统             | 通常最强，但开销更大 |
| 权限控制 | 控制用户或进程能做什么           | 是沙箱的基础机制之一 |

它们不是完全互斥的。实际系统常常会组合使用：在虚拟机中运行容器，再通过操作系统权限和网络规则限制容器中的程序。

沙箱并不等于绝对安全。它的安全性取决于：

- 隔离边界是否实现正确；
- 是否存在权限配置错误；
- 内核或运行时是否有漏洞；
- 是否允许危险的系统调用；
- 是否能通过临时文件、日志、环境变量或网络泄露数据；
- 用户是否批准了过大的权限范围。

因此，沙箱通常采用“最小权限”原则：程序只获得完成任务所需的最低权限。例如，测试代码只需要读项目并运行测试，就不应获得管理员权限或完整网络访问权。

沙箱的常见用途包括：

- 在浏览器中运行网页脚本；
- 执行不可信的插件；
- 打开未知文档；
- 分析恶意软件；
- 运行在线代码；
- 执行 AI 编程代理生成的命令；
- 在 CI/CD 流水线中构建项目；
- 测试新软件而不影响主系统。

对用户来说，判断一个沙箱是否合理，可以看四件事：

1. 程序能读哪些文件？
2. 程序能写哪些文件？
3. 程序能否联网？
4. 程序能否提升到管理员权限？

这四项基本决定了程序出问题时可能造成的影响。

> 那我该如何去确定一个项目的大致方向

确定项目方向时，先不要从“我要用 RAG 还是 Agent”开始，而要从“谁有什么具体问题，我能否在几周内让它变好”开始。技术方案应当服从项目目标。

可以按下面的顺序筛选。

**一、先确定项目类型**

你目前脱产学习，项目通常有三种目的：

- **求职型**：展示完整工程能力，适合做可部署、可演示的作品；
- **效率型**：解决自己或团队的真实问题，最容易获得持续反馈；
- **产品型**：验证别人是否愿意长期使用甚至付费，验证成本最高。

如果现在还没有明确方向，优先选择“求职型 + 效率型”的交集：做一个你自己会用、又能完整展示的工具。

**二、从这四个地方找候选问题**

- 过去工作中反复做、很烦、但又必须做的事情；
- 前端团队中信息分散、沟通成本高的事情；
- 培训班作业中可以继续扩展成真实工具的内容；
- 你自己经常遇到，但目前只能手工处理的问题。

前端背景下，可以重点观察这些场景：

- 看懂大型项目代码；
- 根据需求查找相关组件、接口和文档；
- PR Review、测试用例和问题排查；
- 设计稿到页面实现；
- 团队规范、项目文档和历史 issue 的检索；
- 把自然语言需求转换成结构化任务。

**三、给每个候选方向打分**

每个想法按 1 到 5 分评分：

| 评估项     | 要问的问题                                   |
| ---------- | -------------------------------------------- |
| 痛点强度   | 这个问题是否真的让人浪费时间或容易出错？     |
| 使用频率   | 每周是否会发生多次？                         |
| 用户可得性 | 你能否找到 2 到 3 个真实用户？               |
| 可验证性   | 能否用时间、准确率或完成率衡量改善？         |
| 技术匹配   | 是否确实需要检索、生成、工具调用或多轮流程？ |
| 开发范围   | 能否在 2 到 4 周做出可演示版本？             |
| 展示价值   | 是否能体现你的前端和 AI 应用能力？           |

优先选择总分高、且“用户可得性”和“开发范围”不低于 3 分的项目。一个很酷但没有用户、无法验证的方向，通常不适合作为当前主项目。

**四、把方向写成一句具体的话**

使用这个模板：

> 面向【某类用户】，在【具体场景】下，帮助他们完成【具体任务】，把【某个指标】从【现状】改善到【目标】。

例如：

> 面向前端团队，在排查线上问题时，结合项目代码、接口文档和历史 issue，生成带引用依据的排查步骤，把首次定位时间从 30 分钟降低到 10 分钟。

这比“做一个前端知识库 Agent”具体得多。前者可以验证，后者只是技术名词。

**五、先验证问题，再决定技术**

在写代码之前，找 2 到 3 个目标用户，问他们：

- 最近一次遇到这个问题是什么时候？
- 现在是怎么处理的？
- 哪一步最耗时间？
- 他们是否保存过相关文档、代码或历史记录？
- 如果工具能解决，什么结果才算有用？

如果对方只能说“听起来不错”，却说不出上次真实经历，说明问题还不够明确。

然后做一个很小的验证版本：

1. 先用固定数据和人工整理的结果模拟完整流程；
2. 再接入 RAG 或模型；
3. 最后加入 Agent、工具调用和自动化；
4. 每一步都确认用户是否真的因此少花时间。

不要为了展示技术强行加入 Agent。只有当任务确实需要“拆解任务、检索资料、调用工具、根据结果继续决策”时，Agent 才有意义。单纯的文档问答，可能只需要检索和结构化回答。

结合你的背景，我会优先考虑这三个方向：

- **前端代码与项目文档助手**：适合展示 RAG、引用来源、权限和复杂界面；
- **PR Review 与测试建议工具**：适合展示结构化输出、代码分析和工程流程；
- **需求到页面实现助手**：适合发挥你的前端经验，展示 AI 与交互产品结合。

你现在可以先写出 3 个候选想法，分别套用这个句式：

> 谁，在什么场景下，遇到什么问题；我的工具如何帮助他；成功标准是什么。

然后按上面的 7 个维度评分。最终项目方向不需要一开始就完美，关键是它必须有真实用户、明确任务和可验证结果。

```text
父块：500 到 800 个中文字符
子块：150 到 300 个中文字符
overlap：30 到 50 个字符
```

每个块都保存元数据：

```json
{
  "document_id": 12,
  "file_name": "rag课程.md",
  "title_path": ["RAG", "混合检索", "RRF"],
  "page_number": 8,
  "chunk_index": 23
}
```

必须支持幂等处理。相同文件重复上传时，通过 `file_hash` 判断是否已经处理过，避免重复生成向量。

## 六、RAG 检索流程

在线问答流程：

```text
用户问题
  -> 意图判断
  -> 查询改写
  -> 向量检索
  -> 关键词检索
  -> RRF 融合
  -> Reranker 重排
  -> 相似度阈值判断
  -> 上下文压缩
  -> LLM 生成
  -> 返回答案和引用
```

意图至少区分：

```text
知识问答
练习生成
错题解析
学习计划
普通寒暄
```

只有知识问答进入 RAG 流程，其他任务进入对应服务。

混合检索可以这样配置：

```text
向量召回 Top 20
关键词召回 Top 20
RRF 合并 Top 10
Reranker 重排 Top 5
最终送入模型 Top 3 到 Top 5
```

回答提示词要求：

```text
1. 只能依据提供的资料回答；
2. 资料不足时明确说明；
3. 不要补充没有来源的结论；
4. 每个关键结论附带引用；
5. 引用包含文件名、章节和页码；
6. 先给结论，再给解释和学习建议。
```

引用结构可以设计为：

```json
{
  "text": "RAG 通过外部知识检索补充模型上下文。",
  "document_id": 12,
  "file_name": "rag课程.md",
  "title_path": ["RAG", "基本原理"],
  "page_number": 3,
  "chunk_id": 88
}
```

前端点击引用后，可以展开原文片段。

## 八、练习生成和复习系统

练习题使用结构化输出：

```json
{
  "question_type": "single_choice",
  "question": "RAG 的主要作用是什么？",
  "options": ["...", "...", "...", "..."],
  "answer": "B",
  "explanation": "...",
  "knowledge_point": "RAG基本原理",
  "difficulty": 2,
  "source_chunk_ids": [88, 91]
}
```

模型生成题目后必须经过校验：

- 选项数量是否正确；
- 答案是否存在；
- 解析是否引用知识库；
- 题目是否和当前章节相关；
- 是否与已有题目重复；
- 是否存在多个正确选项；
- 是否出现资料中没有的内容。

评分方式：

- 选择题使用确定性判断；
- 判断题使用确定性判断；
- 简答题使用评分标准和模型辅助判断；
- 模型评分结果必须保留原始答案和评分理由。

复习计划可以先使用简化版间隔复习算法：

```text
首次答错：1 天后复习
连续答对：3 天后复习
再次答对：7 天后复习
持续答对：14 天后复习
答错后重新回到 1 天
```

后续再考虑 SM-2 等更复杂算法。

**认证方案建议**

第一周使用邮箱和密码登录，认证方式采用 HttpOnly Cookie。

流程如下：

```text
注册
  -> 服务端校验邮箱和密码
  -> 密码使用 Argon2id 或 bcrypt 哈希
  -> 创建用户
  -> 自动创建 workspace
  -> 创建登录 session
  -> 写入 HttpOnly Cookie

后续请求
  -> 浏览器自动携带 Cookie
  -> 后端读取 session
  -> 查询当前用户
  -> 校验 workspace 成员关系
```

Cookie 至少设置：

```text
HttpOnly=True
SameSite=Lax
Secure=生产环境开启
Max-Age=7 天或 14 天
```

不建议把长期 JWT 放进 `localStorage`。对于浏览器端 C 端应用，HttpOnly Cookie 更适合第一版，也能在面试中解释 XSS 风险和会话失效处理。

接口建议如下：

```text
POST /api/v1/auth/register
POST /api/v1/auth/login
POST /api/v1/auth/logout
GET  /api/v1/auth/me

GET  /api/v1/workspaces/current
PATCH /api/v1/workspaces/current
```

注册请求：

```json
{
  "email": "user@example.com",
  "password": "至少 8 位",
  "display_name": "学习者"
}
```

注册成功后直接返回当前用户和 workspace，减少前端额外请求。

统一错误格式：

```json
{
  "code": "AUTH_INVALID_CREDENTIALS",
  "message": "邮箱或密码错误",
  "details": null,
  "request_id": "req_..."
}
```

错误码不要让前端根据中文提示判断业务状态。中文信息可以展示给用户，但程序逻辑使用稳定的 `code`。
